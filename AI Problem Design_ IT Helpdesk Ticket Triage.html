AI Problem Design: IT Helpdesk Ticket Triage Classification

1. Problem Statement

Build a text classification system that automatically assigns an urgency label (Low / Medium / High / Critical) to incoming IT helpdesk support tickets based on their subject and description text. This is a narrow, well-bounded supervised classification problem over short-to-medium length text.

Why this problem: IT helpdesks receive a high volume of tickets that currently require a human triage step before routing to the right technician. Manual triage is slow, inconsistent between reviewers, and delays response to genuinely critical issues (e.g., "production server down" vs. "how do I reset my printer password"). Automating the first-pass urgency classification reduces time-to-assignment and improves consistency.

2. Target User

  • Primary user: IT service desk coordinators/dispatchers who currently manually read and route tickets.
  • Secondary user: End users submitting tickets (indirectly benefit from faster response on urgent issues).
  • Use context: The model output is a suggested label shown alongside the ticket in the ticketing system (e.g., Jira Service Management, Zendesk); a human dispatcher can override it. This is a decision-support tool, not a fully autonomous router — at least initially.

3. Data Source

  • Source: Historical ticket export from the organization's existing helpdesk system (e.g., Zendesk/Jira CSV export), containing: ticket subject, ticket description, category tag, and the urgency label historically assigned by a human agent.
  • Size: A small dataset of ~500–2,000 labeled historical tickets is sufficient for this narrow use case (fine-tuning a lightweight classifier or using few-shot prompting with a general-purpose LLM).
  • Labels: Reuse the organization's existing urgency taxonomy (Low/Medium/High/Critical) rather than inventing a new one, to keep labels meaningful to dispatchers and avoid a costly relabeling effort.
  • Data quality note: Historical labels reflect human triage decisions, which may themselves be inconsistent — this is a known limitation addressed in the evaluation section below.

4. Constraints

  • Privacy: Ticket text may contain employee names, internal system names, or sensitive details. Data must be handled under the organization's existing data-handling policy; PII should be scrubbed or the dataset kept internal-only (not sent to external APIs unless the provider is already an approved vendor).
  • Latency: Classification should return a label within a few seconds of ticket submission so it can be shown to the dispatcher in near-real time — rules out heavyweight batch-only pipelines.
  • Class imbalance: "Critical" tickets are rare (~2–5% of volume) relative to "Low"/"Medium" — the model and evaluation must account for this rather than optimizing for raw accuracy.
  • Interpretability: Dispatchers should be able to see why a ticket got a label (e.g., which keywords/phrases drove it), to build trust and support overrides.
  • Scope limit: The system labels urgency only — it does not attempt to route to a specific team/technician or resolve the ticket. That is a separate, later-stage problem.

5. Evaluation Approach

  • Data split: Time-based split (train on older tickets, test on most recent ~20%) rather than random split, since ticket patterns can drift over time and this better simulates real deployment.
  • Primary metrics:
    • Macro F1-score across the four urgency classes (not accuracy alone, given class imbalance) — this weighs performance on the rare "Critical" class equally with common classes.
    • Recall on "Critical" and "High" classes specifically, since a missed critical ticket (false negative) is far more costly than a false positive on a low-priority ticket.
  • Secondary/operational metrics:
    • Disagreement rate with human dispatcher overrides once piloted — if dispatchers frequently overrule a specific label, that's a signal of model weakness even if held-out metrics look fine.
    • Time-to-first-response for Critical/High tickets, before vs. after deployment (the real business outcome this is meant to improve).
  • Baseline for comparison: A simple keyword-rule baseline (e.g., flag "down," "outage," "cannot access production" as High/Critical) — the ML model must clearly beat this simple baseline to justify its complexity.
  • Human-in-the-loop validation: Before full rollout, run the model in "shadow mode" for 2–4 weeks, logging predictions alongside actual dispatcher decisions without acting on them, to measure real-world agreement before it influences routing.

6. AI Model

  • Approach: Given the small dataset (~500–2,000 labeled tickets) and the need for interpretability, a fine-tuned lightweight transformer classifier is preferred over training a model from scratch or relying solely on a large general-purpose LLM.
    • Primary choice: Fine-tune a compact pretrained encoder model, such as DistilBERT or all-MiniLM-L6-v2, as a text classification head over the four urgency classes. These models are small enough to fine-tune quickly on a modest dataset, run cheaply at inference time (supporting the latency constraint), and can be deployed on-premises or in a private cloud environment to satisfy the privacy constraint (no ticket text needs to leave the organization's infrastructure).
    • Alternative/fallback: If labeled data proves too sparse or noisy for reliable fine-tuning, use few-shot prompting with a general-purpose LLM (e.g., Claude or GPT-4-class model) via an approved enterprise API, providing a handful of labeled example tickets per class in the prompt. This trades some interpretability and per-call cost for faster setup and no training pipeline.
  • Interpretability support: Pair the classifier with a simple explainability layer — e.g., highlighting the keywords/phrases (via attention weights or a lightweight technique like LIME/SHAP) that most influenced the predicted label — so dispatchers can see the "why" behind each suggestion, as required by the interpretability constraint above.
  • Model selection criterion: The final model choice (fine-tuned encoder vs. LLM few-shot) should be decided empirically during the pilot, based on which approach better satisfies the Success Criteria (Section 7) on the held-out test set and in shadow mode — not chosen purely on theoretical grounds.

7. Success Criteria

The system is considered successful if, after the shadow-mode pilot:

  1. Macro F1 ≥ 0.75 on the held-out time-based test set.
  2. Recall on "Critical" tickets ≥ 0.90 (minimizing missed emergencies is the top priority, even at some cost to precision).
  3. The model outperforms the keyword-rule baseline by at least 10 points of macro F1.
  4. Dispatcher override rate during shadow mode is below 20%, indicating the suggested labels are broadly trusted and useful rather than routinely ignored.
